# AI 知识库项目启动方法论（前三天总结）

> 项目：基于 Lenny's Newsletter & Podcast 数据的 AI 产品经理问答知识库
> 适用对象：初级 / 入门产品经理
> 范围：Day 1 - Day 3（定义 → 勘察 → 清洗切块）

---

## 一、三天一句话

**Day 1 想清楚做什么，Day 2 看清楚有什么，Day 3 把"有什么"变成"能用的"。**

| 天 | 产品经理视角 | 做了什么 | 产出 |
|---|---|---|---|
| Day 1 | 定义问题 | 写 PRD（用户、场景、边界、验收标准），搭环境，调通 API | PRD、能跑的环境 |
| Day 2 | 摸清原料 | 数据画像：规模、类型、字段、链接覆盖 | 数据画像文档、引用降级规则 |
| Day 3 | 加工原料 | 清洗（去广告、噪音）、切块、加元数据、写校验脚本 | 2,806 个干净的块、清洗报告 |

**贯穿的认知**：AI 产品的效果上限，由数据质量决定。前三天没写一行"AI"代码，却决定了产品能不能做好。

## 二、方法论：AI 知识库启动 5 步法

| 步骤 | 要回答的问题 | 做什么 | 产出 | 过关标准 |
|---|---|---|---|---|
| 1. 定义 | 为谁解决什么问题？ | 写 PRD：用户、场景、范围、**边界规则**、验收指标 | PRD | 能说清"什么问题该答，什么该拒答" |
| 2. 勘察 | 手里有什么数据？ | 数据画像（六步见下） | 画像文档 | 每个发现都落到一个决策 |
| 3. 清洗 | 哪些该删，哪些不能删？ | 写规则，每条规则基于真实样本 | 清洗脚本 + 报告 | 每条删除可审计 |
| 4. 切块 | 检索的最小单位多大？ | 按语义切，带元数据，设重叠 | 带元数据的块 | 块长分布健康 |
| 5. 校验 | 怎么证明洗干净了？ | 把检查写成脚本，每次改规则重跑 | 校验脚本 | 全绿，或红灯有解释 |

**数据画像六步**：多大 → 几种 → 长啥样 → 哪些字段可靠 → 哪里脏 → 所以怎么办。

## 三、关键概念（大白话）

| 概念 | 一句话解释 |
|---|---|
| RAG（检索增强生成） | 开卷考试：先从知识库找资料，再让大模型只依据资料作答，并标注出处 |
| 幻觉 | 大模型一本正经地编造内容，RAG 要解决的核心问题 |
| 元数据（Metadata） | 描述数据的数据，如标题、嘉宾、日期，用于过滤和引用溯源 |
| Token | 大模型计量文字的单位，成本和长度限制都按它算 |
| Chunk（文本块） | 检索的最小单位。整篇压成一个向量会"稀释"语义，所以要切 |
| Overlap（重叠） | 相邻块共享一小段，防止关键内容刚好被切断 |
| Frontmatter | md 文件开头 `---` 包起来的元数据区 |
| JSONL | 一行一个 JSON，存放文本块的通用格式 |

## 五、五条核心原则

1. **先查数据，再定功能。**
   只有约 77% 的文档有原文链接，所以"引用溯源"要设计降级规则，而不是承诺每条都有链接。
2. **全量统计，不靠抽样下结论。**
   读样本是为了理解，统计才是为了证明。只看一篇就会误以为所有文件格式一致。
3. **规则命中 0 次，要回到原数据验证。**
   "brought to you by" 命中 0，并不代表没有广告，只是我猜错了句式。
4. **删除要可审计。**
   每条被删内容写进报告；统计数字突然波动就是找 bug 的线索
   （例如 newsletter 结尾词数从 433 涨到 1,676，发现误截了 1,225 词正文）。
5. **清洗要设收工线。**
   目标是"够用且可审计"，不是零噪音。剩下的由后面的验收题决定值不值得处理。

## 六、可复用模板

### 1. PRD 最小骨架

```
背景问题 / 目标用户 / 核心场景 / MVP 范围（做什么、不做什么）
边界规则：
  - 库内问题：基于检索结果回答并附引用
  - 库外问题：明确告知"知识库中未找到"，不凭模型自身知识作答
  - 闲聊：直接回应，不触发检索
验收指标：检索、生成、行为、工程各至少一条
风险：数据版权、幻觉、数据缺失
```

### 2. 数据画像骨架

```
规模：文件数、总词数、估算 token、单篇长度分布
元数据字段表：字段 / 出现次数 / 可靠性
内容结构：格式特点、噪音清单
引用链接覆盖与降级规则
对下一步的影响：要保留什么、要清洗什么
```

### 3. 清洗规则登记表（每条规则必须填"依据"）

| 对象 | 规则 | 依据（哪个真实样本） | 清理量 | 误伤风险 |
|---|---|---|---|---|
| | | | | |

### 4. 校验清单

```
- 每类噪音至少三个维度交叉检查：句式、公司名、网址
- 通用网（例如所有广告都带 .com/lenny）能抓住没见过的新广告商
- 异常值检查：最短 / 最长的块，看内容而不只看数字
- 白名单：预期内的命中必须登记，否则红灯看多了会被习惯性忽略
- 白名单若按块序号登记，改规则后要重新核对
```

### 5. 每日日志骨架

```
做了什么 / 学到的概念（大白话）/ 关键数据 / 踩坑与解决 / 反思 / 明天计划
```

## 七、常见坑速查

| 坑 | 表现 | 怎么避开 |
|---|---|---|
| 凭经验猜规则 | 规则命中 0 | 先在原数据里搜真实句式 |
| 关键词太宽 | `vanta` 误伤 `advantage` | 用整词匹配 `\b`，命中后看上下文 |
| `grep -w` 不可靠 | 仍命中子串 | 以 Python 正则 `\b` 为准 |
| 假设"之后全是噪音" | 误截 1,225 词正文 | 只删确定的部分，截断类规则必须写明细 |
| 逐段猜广告 | 广告被时间戳切成几段，中间断链 | 找到开头，删到结尾标志 |
| 校验脚本自己误报 | "Hiring?" 出现在正常对话里 | 每个命中都要看上下文 |
| 白名单遮住问题 | 以为清零了，其实是被过滤 | 结论要对照"有无白名单"两种状态读 |
| 前一天的发现没带到后一天 | Day 2 记了 Framer，Day 3 漏了 | 上一阶段的发现变成下一阶段的检查清单 |
| "待复核"凭推断关闭 | 以为广告正文不在稿里 | 用原始数据取证（时间戳空档与广告时长吻合） |

## 八、一句话给初级产品经理

> **做 AI 产品，前期 80% 的功夫在数据上。先定义"什么算好"，再看数据"有什么"，然后清洗并证明"洗干净了"，最后才谈模型。**
