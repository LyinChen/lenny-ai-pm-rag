## 项目定位（为什么这样做）

不做"又一个知识库"，而是做一个**会自己决定"查不查资料"的 AI 助手**（Agentic RAG）。
这是当下企业的主流架构：检索不再是整个产品，而是 Agent 手里的一个工具。

**边界规则（写进了 PRD）**

| 问题类型 | 系统行为 |
|---|---|
| 闲聊 | 直接回答，不检索 |
| 库内问题 | 检索 → 基于资料回答 → 附引用 |
| 库外问题 | 明确告知"知识库中未找到"，不凭模型自身知识作答 |

## 学到的概念（大白话）

- **RAG（检索增强生成）**：开卷考试。先找资料，再让大模型只依据资料作答，答案可追溯。
- **Embedding / 向量**：把文字变成一串数字，意思相近的文字，数字也相近。
- **API Key**：调用模型的密码，等于钱包，绝不能上传到 GitHub。
- **虚拟环境**：项目专属的"隔离房间"，避免不同项目的软件包互相冲突。
- **Agent**：能自己判断"该不该用工具、用几次"的 AI，而不是每次都固定流程。

## 反思（产品经理视角）

1. **先定边界再写代码**。"库外问题怎么处理"是产品决策，不是技术细节。如果不提前定义，模型会"热心地编造"，这就是幻觉风险的来源。
2. **技术选型要匹配时代**。长上下文和 Agent 改变了 RAG 的位置：它从"产品本身"变成"组件"。所以我把项目从基础问答升级为 Agentic RAG。
3. **指标要先于功能**。PRD 里先写了验收标准（Hit Rate@5 ≥ 80%、Faithfulness ≥ 0.8、库外拒答 100%），后面每一步都有了方向。
